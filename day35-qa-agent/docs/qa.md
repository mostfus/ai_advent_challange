# QA agent

A test scenario in words, carried out on an iOS app in the Simulator by a model: the verdict, every check with its evidence, a screenshot per step, a crash report, the cause of a failure in the code, and a passed run as an XCUITest. Why and what it showed: [README](../README.md#qa-agent---the-real-task-day-35).

## The pieces

```
static/qa.js ── /api/qa/* ── core/services/qa.py (QaService: one job at a time)
                                   │
            ┌──────────────────────┼─────────────────────────────┐
     qa/xcode.py             qa/runner.py                    qa/bridge.py
     schemes, a build        QaRun, execute(), verdict()     xcodegen + build-for-testing,
     for the simulator            │                          testServe in the background,
     qa/simctl.py                 │ core/agent.Agent         the generated tests' runs
     devices, apps,               │ (calls one after another)         │
     install, screenshot          ▼                                   │ HTTP on 127.0.0.1:22087
                       tools/simulator.py ─────────────────────────────►  bridge/UITests/BridgeTests.swift
                       SimulatorProvider: look, tap, type_text,            XCUITest, on the main thread:
                       scroll, launch_app, wait, check, finish             /tree /tap /type /swipe /launch ...
                       render_screen(): the tree as text with refs
                                  │
                       qa/crash.py (.ips)   qa/diagnose.py (read-only FilesProvider)
                       qa/xcuitest.py → qa_suite/tests/*.swift   qa/suite.py → qa_suite/suite.json
```

### The bridge (`bridge/`)

XCUITest can drive any installed app by its bundle id, but only from inside a UI test. So the bridge is a UI test that does not end: `BridgeTests.testServe` starts an HTTP server (`BridgeServer.swift`, Network.framework, bound to 127.0.0.1 - the simulator shares the Mac's loopback) and runs each request on the test's main thread, the only one XCUITest may be used from. The network thread waits for the answer. A failed XCUITest call (no keyboard focus, an app that is gone) records an issue instead of throwing; `record(_:)` catches it while serving, so the command answers with the reason and the bridge keeps running.

| Command | What |
|---|---|
| `GET /health` | Is it up |
| `POST /launch {bundle_id, fresh}` | Launch from scratch, or bring forward |
| `POST /tree {bundle_id}` | The app's accessibility hierarchy (type, label, identifier, value, placeholder, frame, enabled, selected), and a system alert if one is up |
| `POST /tap {x, y, duration}` | A tap (or long press) at a point, in screen points |
| `POST /type {bundle_id, text}` | Type into the focused field (`\n` is Return) |
| `POST /swipe {from, to}` | Press and drag - a scroll |
| `POST /state`, `/terminate`, `/home`, `/shutdown` | |

The Xcode project is generated by XcodeGen from `project.yml` and never committed: an empty host app (a UI-testing bundle needs a target app) and the `QABridgeUITests` target, which also compiles `QASupport.swift` (the helpers generated tests call) and the suite's tests - the folder in `QA_TESTS_DIR`, this app's `qa_suite/tests` or another repository's suite in CI. `qa/bridge.py` regenerates and rebuilds only when a source changed (a fingerprint of the Swift files and the spec), into `data/qa/bridge-build`, and starts it with `xcodebuild test-without-building -only-testing:QABridgeUITests/BridgeTests/testServe`, the port passed as `TEST_RUNNER_QA_BRIDGE_PORT`. It is started on the first run, kept between runs, and stopped with the app.

### What the model sees (`tools/simulator.py`)

```
App: Modern Collection Views | State: foreground | Screen: 402x874 points
NavigationBar "Mountains Search"
  [e1] Button "Modern Collection Views" id=BackButton
[e3] SearchField value="K2" at 201,148
  [e4] Button "Clear text"
[e5] CollectionView
  [e6] Cell "K2"
The keyboard is up: type_text types into the focused field
```

The tree is cut to controls, texts and their containers: decoration inside a cell is dropped, an accessory listed twice is shown once, a cell's texts go on its line, a switch reads `= on`, an empty field shows its placeholder, what is off the screen is counted ("3 more element(s) below - scroll down"), a scroll bar becomes "(scrolls: 13 pages)", and a system alert comes first. A screen is 300-1500 characters. Refs belong to one screen; `tap(ref)` taps the middle of the element's visible part.

Every action answers with the screen it led to and says when the screen did not change, when the app went to the background, or when it is not running any more - then the crash report (`qa/crash.py`: the newest `.ips` of that bundle id since the run started, its exception, Swift's message and the crashed thread's frames) is in the answer.

The calls of one round run one after another (`Agent(parallel_calls=False)`) and the provider takes a lock: two taps asked together are two taps in a row.

### A run (`qa/runner.py`)

1. The app is launched from scratch; its first screen goes into the first message with the scenario.
2. The model drives it with the tools; `check` records each expectation (passed or not, the evidence refs, the `examples` of a live list, the texts that must be absent, a note), `finish` the model's own verdict.
3. The verdict is computed: a crash → `crashed`; a failed check → `failed`; stopped by the person → `stopped`; then the model's `failed`/`blocked`; `passed` only with at least one check (`unchecked` otherwise); no finish → `incomplete`.
4. A `failed` or `crashed` run, with diagnosis on, goes to `qa/diagnose.py`: an agent with `FilesProvider(read_only=True)` over the project open in the Project tab (in CI: the app's checkout) and, when its index is built, `search_docs`.
5. `run.json` and the screenshots are kept in `data/qa/runs/<id>/`.

### A passed run as a test (`qa/xcuitest.py`)

```swift
let app = QA.launch("com.example.apple-samplecode.modern-collection-viewsDY5L757WXL")

// Step 2: Open Diffable Data Source section - Cell "Diffable Data Source"
QA.tap(app.cells["Diffable Data Source"].firstMatch)
...
// Check 1: Wi-Fi включён и показан список сетей
QA.expectValue(app.switches["Wi-Fi"].firstMatch, "1", "Wi-Fi включён и показан список сетей")
QA.expectRows(app.cells, besides: ["Wi-Fi"], "Wi-Fi включён и показан список сетей")
```

An element is found by identifier, else label, else the text inside it (`app.cells.containing(.staticText, identifier: "K2")`), else - a field - the first of its kind, and only when nothing names it by its point. A step that failed is left out. The test goes into `qa_suite/tests/<Class>.swift` and its scenario into `qa_suite/suite.json`; **Run test** in the tab, or CI, runs it with the bridge's build, without a model.

## In CI

```yaml
# .github/workflows/qa-agent.yml (repository root), in short
on:
  pull_request: {paths: ["day35-qa-agent/**", ".github/workflows/qa-agent.yml"]}
  workflow_dispatch: {inputs: {scenario: ..., model: ...}}
jobs:
  qa:
    runs-on: [self-hosted, macOS]
    steps:
      - uses: actions/checkout@v5
      - uses: actions/checkout@v5
        with: {repository: mostfus/UIKitDeepCollectionView, path: qa-app}
      - uses: ./day35-qa-agent/qa-action
        with: {project-path: qa-app, deepseek-api-key: "${{ secrets.DEEPSEEK_API_KEY }}"}
      - uses: actions/upload-artifact@v4      # the runs: run.json, report.md, screenshots
```

`qa-action/action.yml` runs `python -m qa` (`qa/__main__.py`):

1. the simulator (`--device`, else the suite's, else `qa_agent.json`'s) is booted if it was not - and shut down again at the end;
2. the app is built from the checkout (`--container`/`--scheme`, else the suite's `app`) into the report folder and installed;
3. every scenario (or `--scenario ID`) is run by the model, a failure diagnosed in the checkout's code;
4. the bridge is stopped and every generated test is run;
5. `summary.md` - a table of scenarios and of tests, the diagnoses folded - becomes the job summary and, in a pull request, one comment (updated on every push, with `GITHUB_TOKEN`).

Exit code 1 when a scenario did not pass or a test failed; 2 when the suite could not run (no simulator, a failed build, no key).

Inputs of the action: `project-path` (required), `suite`, `container`, `scheme`, `device`, `model`, `scenario`, `deepseek-api-key`, `github-token`, `out`. Another repository can use it as `mostfus/ai_advent_challange/day35-qa-agent/qa-action@<full commit SHA>` with its own `suite`.

### The runner

- Xcode with an iOS simulator runtime; `brew install xcodegen uv`.
- The repository secret `DEEPSEEK_API_KEY` (the reviewer's, day 32).
- Pull requests from forks never reach it (the job's `if`), and the job is one at a time (`concurrency: qa-agent`): one simulator, one bridge port.
- An x86_64 runner package under Rosetta starts Xcode's tools as arm64 (`qa/simctl.native`).

## Limits

- Simulator only.
- The accessibility tree, not pixels: layout, images and colours are not checked; unlabeled controls are reached by position.
- Live data in a check needs the scenario to say it is live, or the generated test asserts today's rows.
- One job at a time per app instance and runner.
